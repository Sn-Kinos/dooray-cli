## ADR-069: 나머지 공식 endpoint 는 명세 표 한 줄씩으로 두고 명령은 생성기가 만든다

**결정**: 직접 쓴 명령이 감싸지 않은 공식 endpoint 는 `src/api/endpoints/*.ts` 에 `EndpointSpec` 한 줄씩 적는다.
`src/commands/endpoint-command.ts` 의 `mountEndpoints` 가 그 표를 읽어 기존 명령 나무에 명령을 단다.
서비스 API 와 관리 API 를 같은 방식으로 다룬다.

- 경로의 `{...}` 자리는 순서대로 positional 인자다. `{project-id}` 는 프로젝트 코드도 받아 기존 resolver 로 푼다.
- 쿼리 파라미터는 이름을 kebab-case 로 바꾼 옵션이다.
- JSON 본문은 `--data <json>` 또는 `--data-file <path>` 로 받는다. 둘 다 `-` 면 stdin 이다. 19자리 정수는 문자열로 보존한다 (ADR-051).
- multipart 업로드와 파일 다운로드는 307 을 따라간다 (ADR-015). 다운로드는 `-o`·`--output-file` 을 따른다 (ADR-067).
- DELETE 와 명세에 `destructive` 를 적은 호출은 확인을 거친다 (ADR-036).
- 출력은 기본이 `result` 의 YAML, `--json` 이 응답 그대로, `--quiet` 가 `result` 의 `id` 다. 응답에 `cursor` 가 있으면 stderr 로 알린다.
- GET 이 아닌 호출이 성공하면 캐시 전체를 비운다.
- 경로가 `admin/` 으로 시작하면 `adminApiKey` 와 관리 API 주소로 부른다. 주소는 `adminBaseUrl` 이 없으면 `baseUrl` 의 `api.` 를 `admin-api.` 로 바꾼다. 네 클라우드 모두 이 규칙을 따른다.

**맥락**: 2026-10-12 기준 공식 서비스 API 137개 중 CLI 가 쓰는 것은 54개였고 관리 API 126개는 하나도 없었다.
남은 200여 개를 지금까지처럼 명령 파일 하나, 클라이언트 메서드 하나, 응답 타입 하나씩 손으로 쓰면 수천 줄이 늘고, 문서와 어긋나는 지점도 그만큼 는다.
남은 endpoint 대부분은 경로·쿼리·본문을 그대로 넘기면 되는 CRUD 라 명령마다 다른 판단이 필요하지 않다.

**기각한 대안**:

- **endpoint 마다 손으로 쓴 명령**. 위와 같은 이유로 기각했다. 이름 해석, 편집기, 표 출력처럼 판단이 필요한 명령은 지금처럼 손으로 쓴다. 표의 명령이 그런 손질이 필요해지면 표에서 빼고 손으로 쓴 명령으로 옮긴다.
- **`dooray api <METHOD> <path>` 하나만 두기**. 모든 endpoint 를 부를 수는 있지만 사용자가 경로와 파라미터 이름을 문서에서 찾아야 한다. `--help` 에 무엇이 있는지 보이지 않는다.
- **본문 필드마다 옵션 두기**. 필드 이름과 중첩이 endpoint 마다 달라 생성기가 커진다. 필드 요약을 `--data` 도움말에 싣는 것으로 멈췄다.
- **쓰기 결과로 캐시를 엔티티별로 지우기**. 어떤 endpoint 가 어떤 캐시 파일을 깨는지 표에 적어야 한다. 캐시는 다시 받으면 되므로 전체를 비운다.

**검증**: `pnpm api:inventory` 는 클라이언트와 명세 표를 함께 읽어 공식 목록과 대조한다.
관리 API 목록은 `docs/api/official-admin-endpoints.txt` 에 따로 둔다.
`scripts/api-endpoint-inventory.test.mjs` 가 표의 모든 줄이 인벤토리에 읽히고 공식 목록에 있는지 본다.

**API 가 아닌 두 절**: 같은 목차의 「커스텀 사이드 앱」과 「OAuth」에는 CLI 가 부를 endpoint 가 없다.
사이드 앱은 Dooray 가 고객 서버를 부르고, OAuth 는 Dooray 가 고객사 SSO 의 클라이언트가 되는 설정이다.
그래서 명세 표가 아니라 직접 쓴 명령으로 그 반대편을 맡는다. `side-app serve`·`verify`·`check` 는 Dooray 가 부를 서버와 JWT 검증을,
`sso check` 는 담당자에게 넘길 OIDC 메타데이터 점검을 한다. 문서가 인증 토큰을 HMAC 키로 쓰는 방식(문자열 그대로인지 base64 인지)을
정하지 않아 둘 다 시도한다.

**실측 (2026-10-12)**: 실제 계정에서 개인 드라이브·테스트 캘린더·나에게 보낸 메시지·개인 프로젝트 단계로 쓰기 명령을 만들고 지우며 확인했다.
시험용 일반 프로젝트를 만들어 수정, 업무 상태·템플릿·메일 주소·Hook·위키 Hook, 업무 이동과 담당자별 상태, 임시 업무와 첨부를 확인한 뒤 보관했다.
`hook create` 는 개인 프로젝트와 새로 만든 프로젝트 모두에서 CLI 없이 직접 호출해도 500 이 난다.
혼자 있는 대화방에서 `channel member leave` 는 되지만, 그 뒤 `join` 은 500 이다. 나가면서 방이 닫히는 것으로 보이며 다른 멤버가 있는 방에서는 확인하지 않았다.
관리 API (2026-10-13) 는 조회만 실제 계정으로 확인했다. 조직·멤버·부서·직책·직위·고용형태·근무지·메일 도메인·메일 그룹 목록, 멤버·이메일 주소 단건, 그리고 본인 기준의 담당 업무·일정·예약 가능 자원·최근 게시글·메일 목록이 성공했다.
관리 API 의 쓰기는 테넌트 전체에 영향을 주므로 목 서버 테스트로만 확인했다.
쿼리 이름의 `_` 는 옵션에서 `-` 로 바꾼다 (`board_id` → `--board-id`).
